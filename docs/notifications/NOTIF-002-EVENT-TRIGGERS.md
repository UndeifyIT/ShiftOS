# 1. Purpose

This document defines how operational events generate notifications within ShiftOS.

Event Triggers determine which business events should create notifications and which users should receive them.

Notifications are generated automatically after business rules evaluate the triggering event.

---

# 2. Trigger Philosophy

Operational domains publish events.

The Notification Service decides whether notifications should be generated.

This separation keeps business logic independent from notification delivery.

---

# 3. Event Workflow

The standard workflow is:

```
Business Event Occurs

↓

Event Published

↓

Notification Rules Evaluated

↓

Eligible Recipients Identified

↓

Notification Created

↓

Delivery Process Started
```

---

# 4. Trigger Sources

Notifications may be triggered by events from any operational domain.

Examples include:

### Organization

- User invited.
- Organization settings updated.
- Branch created.

---

### Employee

- Employee assigned to a branch.
- Employment status changed.
- Employee profile updated.

---

### Schedule

- Schedule created.
- Schedule published.
- Schedule updated.
- Schedule locked.

---

### Shift

- Shift assigned.
- Shift reassigned.
- Shift cancelled.
- Shift updated.

---

### Attendance

- Clock in recorded.
- Clock out recorded.
- Late arrival detected.
- Attendance correction approved.

---

### Tasks

- Task assigned.
- Task due soon.
- Task overdue.
- Task verified.

---

### Communication

- Announcement published.
- Acknowledgement required.
- Reminder generated.

---

### Security

- Password changed.
- Account suspended.
- New device login.
- Permission updated.

---

### Shifty

- Recommendation generated.
- Productivity suggestion available.
- Operational insight detected.

---

# 5. Trigger Evaluation

Every event should be evaluated using business rules before notifications are generated.

Evaluation considers:

- Organization.
- Branch.
- User role.
- User permissions.
- Notification preferences.
- Event priority.

Not every event results in a notification.

---

# 6. Recipient Resolution

The Notification Service determines recipients based on:

- Event type.
- Organization membership.
- Branch assignment.
- Role.
- Visibility rules.
- Organization policies.

Only eligible users receive notifications.

---

# 7. Duplicate Prevention

The Notification Service should avoid generating duplicate notifications for the same event.

Examples include:

- Multiple updates within a short period.
- Repeated status changes.
- Identical reminder events.

Where appropriate, existing notifications should be updated instead of creating new ones.

---

# 8. Deferred Triggers

Some notifications should be scheduled rather than generated immediately.

Examples include:

- Upcoming shift reminders.
- Task due reminders.
- Pending acknowledgement reminders.
- Expiring schedule drafts.

Deferred notifications should be generated by scheduled background jobs.

---

# 9. Permissions

Event Triggers do not bypass authorization.

Notifications are generated only for users who are permitted to receive information about the underlying event.

Permission checks occur before notification creation.

---

# 10. Database Considerations

Notification generation should use:

```
notifications

notification_preferences

organization_memberships

branch_assignments
```

Operational events remain owned by their originating domains.

The Notification Service should reference those events rather than duplicate their data.

---

# 11. Audit Requirements

The following events may generate audit records:

- Notification created.
- Notification suppressed.
- Recipient resolution completed.
- Notification generation failed.

The originating operational event continues to be audited by its respective domain.

# 14. Summary

Event Triggers define how operational events become notifications within ShiftOS.

By separating event generation from notification delivery, ShiftOS maintains a scalable, maintainable and extensible notification architecture while ensuring that users receive timely, relevant and authorized operational updates.
